USED CAR RETAIL OS —— 门店车辆全生命周期经营流程说明（业务口径版）
适用门店：杭州旗舰店（企业版） · 文档范围：收车、库存、定价、成交、售后、清库、审批、预警、员工交接 · 不含 AI 收车 / 智能问答模块，不含代码实现细节

一、文档定位与范围

结论：本文按「一辆车从收进来到退出库存」的顺序，把系统里已经落地的全部业务流程讲完，每个环节只讲业务规则和数据口径，不讲技术实现。

覆盖范围（全部为系统内已实现的业务）：

  • 车辆主线：收车入库 → 挂牌在售 → 成交登记 → 售后跟踪 → 清库退出，以及各环节的撤回路径。
  • 经营支撑：成本记账、定价测算与调价、车辆证件、客户档案、库存预警。
  • 管理控制：员工角色权限、写操作审批流、员工离职交接。

明确不在范围内：AI 收车与智能问答能力；在线支付、合同电子归档、短信触达、报表导出这四项系统目前不做，流程描述中也不会出现。

二、角色与权限

结论：系统只有两种角色——管理员（老板）与员工。差别只有一条：员工发起的写操作必须经管理员审批后才生效，管理员的写操作直接生效。

能力管理员（ADMIN）员工（EMPLOYEE）
查询（车辆、客户、订单、预警、审批单等）不限制不限制
业务写操作（收车、调价、成交登记等 10 类）直接执行，即时生效只生成待审批单，批准前不生效
审批（批准 / 驳回）可操作不可操作
撤回 / 复制重提审批单可操作只能撤回或重提自己提交的待审批单
员工管理（新增、编辑、停用）可操作不可操作
离职交接（指定接手人并批量流转车辆）可操作不可操作
员工账号只做停用、不做删除，历史单据与流水永远保留真实的操作人。

三、核心业务对象与编号规则

结论：业务以「车辆」为中心，客户、订单、售后、证件、成本、预警、审批单、交接记录都挂在具体车辆或具体员工上。

对象业务含义编号 / 关键字段规则
车辆一台在库或已流转的二手车，是全流程主线库存编号 = UC + 年月日 + 3 位当日流水（如 UC20261105001）；状态为五态之一
客户买方 / 卖方 / 双重身份的自然人档案手机号为查重主依据，同一手机号不允许重复建档
成交订单一次车辆买卖成交的书面记录订单号 = SO + 年月日 + 3 位当日流水；一台车最多一条成交订单
售后单成交后客户反馈的问题（维修 / 退款 / 投诉 / 其他）状态：待处理 → 已结案
成本记录这台车花出去的每一笔钱类型：收车款 / 整备 / 运输 / 过户 / 其他（售后成本也记在这里）
车辆证件登记证、行驶证、交强险、年检登记证编号 + 到期日期，到期日驱动预警
库存预警每日巡检产出的经营待办类型：滞销 / 毛利过低 / 证件到期；状态：待处理 → 已处理 / 已忽略
审批单员工写操作提交给管理员的待批申请单号 = SP + 年月日 + 3 位当日流水；状态：待审批 / 已通过 / 已驳回 / 已撤回
交接记录离职时车辆对接人变更的留痕只追加、不修改，一车可有多条形成完整流转链

四、主链路：车辆生命周期

结论：一辆车的一生是五态单向主线——已收车 → 在售 → 已成交 → 售后 → 已清库；在此之上只额外开放四类撤回 / 例外流转，其余组合一律拒绝。

4.1 状态流转矩阵（完整口径）

当前状态允许流转到业务条件（在状态本身之外叠加）
已收车在售无附加条件；不允许跳过在售直接成交，否则挂牌价与调价记录断链
在售已成交、已清库成交须走「成交登记」环节（见 5.7）；直接清库适用于车况重大瑕疵转批发等场景
已成交在售（撤回）、售后、已清库撤回成交用于纠正误登记；转售后见 5.8；清库前须无未结案售后单

五、业务环节详述

5.1 收车入库

结论：收车是一次「建档 + 记账 + 留痕」的原子动作——车辆档案、收车款成本、状态流水在同一事务里写完，缺任何一件都不算入库成功。

  • 必填信息：品牌、车型、收车价、收车日期。
  • 建议信息：VIN 车架号、首次上牌日期、表显里程、车牌号（可后补，后补走「修改车辆信息」）。
  • 入库即写三类记录：
    1. 车辆档案：状态固定为「已收车」，生成库存编号（UC+年月日+3 位流水）；
    2. 成本记录：收车价记为第一笔「收车款」成本（否则后续所有成本合计都是 0）；
    3. 状态流水：首条流水「无来源状态 → 已收车」。
  • 归属规则：录入人记入「创建人」；车辆对接人可指定其他员工，未指定时默认等于录入人。经审批入库的车，创建人记申请人而非审批人。
  • 挂牌价：收车时可以填一个初始挂牌价，但首次挂牌价（降价基准）此刻不定格，等真正转「在售」那一刻才定格（见 5.2）。

5.2 挂牌在售

结论：转「在售」这一步做两件事——状态推进 + 定格降价基准，之后的调价都不再改动这个基准。

  • 车辆状态：已收车 → 在售。
  • 降价基准（首次挂牌价）在这一刻定格；之后再怎么调价，阶梯降价都以这个基准算，而不是以「最近一次挂牌价」算。
  • 转「在售」后，定价测算、库存预警才开始对这台车生效。

5.3 成本管理

结论：这台车花的每一分钱都必须进成本明细，成本合计直接决定保本底价与毛利测算。

成本类型典型场景录入时机
收车款付给卖方的车款收车入库时自动记一笔，金额 = 收车价
整备维修、美容、易损件更换发生后手动追加
运输拖车、板车、异地提车运费发生后手动追加
过户过户费、上牌代办费发生后手动追加
其他杂费；售后成本也自动记为这一类手动追加 / 售后单带出

5.4 定价测算与调价

结论：系统按「总成本 → 资金成本 → 保本底价 → 阶梯建议价」四步算出建议价格和亏损红线；所有业务参数放在规则表里，门店可调、改完约 30 秒生效，代码里不写死任何数字。

总成本 = 收车款 + 全部追加成本（整备 / 运输 / 过户 / 其他，含售后成本）
持有天数 = 收车日期 → 测算当日（录成未来日期按 0 天计，不产生负资金成本）
资金成本 = 总成本 × 年化率（默认 8%）× 持有天数 ÷ 365
保本底价 = 总成本 ×（1 + 保本加成，默认 5%）+ 固定费用（默认 2,000 元）
阶梯建议价 = 首次挂牌价 ×（1 − 阶梯幅度）；持有 45 / 60 / 75 天分别对应 3% / 8% / 13%，命中最高一档、只降一次不累加
预期毛利 = 当前挂牌价 − 总成本 − 资金成本
两套口径提醒（解释面试官追问用）：保本底价含 5% 保本加成与 2,000 元固定费用，代表「卖到这个价才不亏」； 预期毛利不含这两项，代表「按当前挂牌价卖出去的账面进账」。两者用途不同，数值天然不一致。
  • 保本判定：当前挂牌价 < 保本底价，即视为跌破保本线，会触发「毛利过低」预警。
  • 滞销分级（默认阈值，同在规则表可调）：持有 45 / 60 / 75 天分别进入「关注 / 预警 / 严重滞销」。
  • 调价：员工或管理员发起「调整挂牌价」，需填新价格与调价原因；每次调价都留价格变更记录（旧价、新价、原因、操作人），可回溯。调价不影响已定格的首次挂牌价基准。

5.5 证件管理

结论：每台车挂四类证件（登记证 / 行驶证 / 交强险 / 年检），系统按到期日提前 30 天自动提醒。

  • 登记时填证件类型、证件编号、到期日期，可附文件。
  • 证件可新增、可删除，两类操作都走审批（员工发起时）。
  • 到期提醒进「库存预警」列表（证件到期类），处理后不再重复提醒该证件。

5.6 客户管理

结论：客户档案独立维护，成交时把「买方客户」关联到订单上；手机号是唯一查重依据。

  • 客户类型：买方 / 卖方 / 双重身份；客户等级：普通 / VIP。
  • 建档必填姓名、手机号；同一手机号不允许重复录入。
  • 支持按姓名或手机号模糊检索；客户本身不直接挂车辆，关联发生在成交订单上。

5.7 成交登记

结论：成交是独立登记动作，不是「点个状态顺手记一下」——先写订单、再把车推进「已成交」，两件事同一事务完成。

  • 前提：车辆必须是「在售」；买方客户必须已在客户档案里；一台车只能有一条成交订单（重复登记会被拒绝）。
  • 订单内容：订单号（SO+年月日+3 位流水）、买方客户、成交价、成交日期、付款方式（全款 / 按揭）、定金、备注。
  • 销售归属：订单的成交销售默认取该车的对接人，不允许前端另行指定。
  • 状态推进：订单写入成功后，车辆状态：在售 → 已成交，并留状态流水「成交登记 + 订单号」。
  • 撤回：误登记或订单未成立时，可撤回成交，车辆回到「在售」；撤回后允许重新登记成交。

5.8 售后处理

结论：售后单跟踪成交后的问题直到结案；售后成本同步进成本账，未结案的售后单会卡住清库。

  • 新开售后单：车辆未清库即可登记（不限于「售后」状态）；字段为问题类型（维修 / 退款 / 投诉 / 其他）、问题描述、售后成本。
  • 成本联动：售后成本 > 0 时，自动追加一笔「其他」类成本记录，成本合计、保本底价、毛利测算同步变化。
  • 结案：售后单从「待处理」到「已结案」，记录结案时间。
  • 清库联动：只要还有未结案售后单，清库一律拒绝；已清库的车不允许再新增售后单。

5.9 清库

结论：清库是车辆退出经营库存的终点动作，前提只有一个——售后闭环；清库后冻结信息修改，只留一条受控的撤回通道。

  • 可清库的来源：在售（如重大车况转批发）、已成交（客户当场提走无售后）、售后（已结案）。
  • 清库前校验：无未结案售后单（从「已清库」撤回时不再重复校验，避免逻辑死锁）。
  • 清库后限制：不允许再修改车辆基础信息，不允许新增售后单。
  • 清库撤回：只能恢复到最近一次流转前的那个状态，恢复后历史流水、成本、订单记录全部原样保留。

六、写操作审批流

结论：员工的每一笔业务写操作都先变成待审批单，管理员批准时按「申请提交时的内容快照」执行；执行失败整单退回待审批，不会出现「单据显示通过但业务没落地」。

6.2 审批单规则

  • 快照执行：批准时按员工提交那一刻的申请内容执行，不是按「当前表单」执行；归属记申请人，审批人另记。
  • 复制重提：被驳回 / 已撤回的单子可以「复制一份新的待审批单」再交；原单永久留档作历史。「删除证件」「售后结案」两类没有可改参数，只能原样重提。
  • 并发防护：同一张待审批单只允许被批准（或驳回）一次，重复点击不会执行两遍业务。
  • 写操作结果：员工发起时统一返回「已生成待审批单」或「已执行」两种结果，界面据此提示。

八、员工管理与离职交接

结论：离职不只是改个员工状态——名下所有未清库车辆的对接权要一次性交接出去并留痕，历史记录一律不动。

8.1 员工管理

  • 仅管理员可新增、编辑、停用员工；只停用不删除，保证历史单据能追到真实的人。
  • 员工被停用后不能登录，但其创建的车辆、提交的审批单、处理的售后全部保留。

8.2 离职交接

  • 「未完成」口径：对接人是该员工、且状态不是「已清库」的车辆（已清库视为完成，不参与交接）。
  • 操作流程：管理员发起离职 → 界面提示「将流转几辆车」→ 指定接手人 → 一次性批量流转。
  • 流转内容：只改车辆对接人这一个字段；创建人、状态流水、调价记录、审批记录、订单、售后全部原样保留。
  • 交接留痕：每辆车写一条交接记录（原对接人 → 接手人、操作人、原因），一辆车被流转多次也能查到完整链条。
  • 原子性：离职状态变更与批量车辆流转同事务，中途失败全部回滚，不会出现「人已离职、车还在他名下」的中间态。

九、全局红线汇总

结论：下面 8 条是贯穿全流程的硬约束，任何环节触碰都会被拒绝，且都有留痕。

#红线适用环节
1状态流转必须走状态机白名单，非法组合一律拒绝全部状态变更
2未结案售后单存在时禁止清库清库
3一台车最多一条成交订单成交登记
4降价基准（首次挂牌价）只在首次挂牌时定格，之后调价不再改动它挂牌、调价、定价测算
5已清库车辆禁止修改信息、禁止新增售后单车辆维护、售后
6员工写操作未获批准前不得生效；批准按申请快照执行审批流
7收车入库的档案、成本、状态流水三者同事务，缺一不成立收车入库
8客户手机号唯一；离职交接只改对接人、不抹历史客户建档、离职交接
定价参数说明：年化率、保本加成、固定费用、阶梯天数与幅度、滞销阈值、证件提醒天数共 14 项参数全部存放在定价规则表中， 本文所列默认值（8% / 5% / 2,000 元 / 45-60-75 天 / 3%-8%-13% / 30 天）为门店当前配置，不代表行业标准值。
